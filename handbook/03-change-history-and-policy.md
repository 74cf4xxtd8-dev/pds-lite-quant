## 5. 필수 테스트와 배포 승인 원칙

### 5.1 변경 절차
1. main에 직접 push하지 않는다. 모든 변경은 **별도 브랜치 → Draft PR**로 한다. 문서만 바꾸는 변경도 같다.
2. PR마다 `tests` CI(offline + live)가 돈다. 작업 요약에서 비교 기준 SHA, 파이프라인 경로 변경 여부, 회귀 보고를 확인한다.
3. 소유자가 diff·CI·보고를 검토한 뒤 **명시적으로 승인**해야 Draft 해제·병합한다. 승인 전에는 병합하지 않는다(Pages 배포도 main 병합으로만 일어나므로 같은 원칙).
4. 병합 뒤 확인(5.4절)에서 이상이 있으면 추가 수정·재실행 없이 `PDS_HALT`를 걸고 보고한다(5.5절).
5. 코드·워크플로·화면이 바뀌면 **같은 PR에서 이 handbook의 해당 절도 고친다.**

### 5.2 필수 통과 (실패 시 병합 불가)
- Fail-safe: 무결성 검사, 실패 시 무기록, 워크북 없음 → RB = 1, 진단 모드 격리.
- 잠금 조건: F2R 공식 대기, 원작자 Core 일치, 10일 마감, 마감 뒤 자동 잠금 없음.
- 수동 해제·승인: 자료·입력 검사, 승인 규칙 10가지, 본인 재확인 vs 독립 승인.
- 운영자 중지: 신규 잠금 없음, 운영 데이터 바이트 불변, 값 해석, 알림 1회.
- 추가 전용: 잠금·원장·감사·해제 기록, **커밋된 잠금 파일 바이트 불변**.
- 실데이터: **원작자 공개 Core 116/116(잠금 개월 수만큼) 일치**, 커밋된 잠금 위에서 신규 잠금·변경 없음.
- 워크플로 배선(예약·권한·단계 순서·입력값 셸 삽입 금지), 커밋 단계 fail-safe, 알림 전달·재전송.
- 화면이 읽는 JSON 필드 유지.
- 테스트는 실제 `docs/data`를 건드리면 실패한다(`conftest.py`).

### 5.3 변경 유형별 추가 확인
| 변경 | 추가 확인 |
|---|---|
| 파이프라인 경로(`run_pipeline.py`, `requirements.txt`, `tools/`, `update.yml`) | 롤백 검증(대상 커밋 코드가 이 브랜치 파일을 읽어도 잠금을 바꾸거나 빈 달을 채우지 않는지)이 자동으로 돈다. 회귀 보고에서 Core·공식 목표 차이 확인 |
| Core 계산 함수 | 실데이터 116/116. 필요하면 라벨 `v10-migration`으로 v1.0 비교도 실행 |
| 워크플로 | `test_workflow_defaults_and_schedule`, `ops-audit`의 쓰기 권한 점검. 새 워크플로에 `contents: write`를 주지 않는다 |
| 화면 | `test_dashboard_flag_view_per_tab`, `test_payload_keeps_every_field_the_dashboard_reads`, 실제 휴대폰 확인 |
| 문서 | 문서 속 파일명·함수명·설정값·일정이 코드와 같은지 대조 |

### 5.4 병합 뒤 확인
1. 파이프라인 경로가 바뀌었으면 push로 update-portfolio가 1회 자동 실행된다. 성공 여부를 확인한다.
2. `official_history.json` 바이트 불변(기존 달), 신규 잠금이 예상과 같은지 확인한다.
3. 공식 목표 수치, `run_status.json`(ok, action), Telegram(상태 변화가 있을 때만), Pages 배포를 확인한다.

### 5.5 이상 징후가 있을 때
추가 코드 수정이나 재실행을 임의로 하지 않는다. 잠금 또는 공식 목표가 예상과 다르면 `PDS_HALT=1`을 걸고(② 7장) 보고한다. 운영 중단 여부는 소유자가 판단한다.

### 5.6 테스트에 대한 원칙
기존 테스트의 의미나 안전성 검증 범위를 줄이는 변경은 하지 않는다. 필요하면 먼저 보고하고 승인을 받는다.

## 6. 운영 정책과 주의사항

### 운영 정책
1. **실행 기준은 Official뿐이다.** WAIT·BLOCKED·운영자 중지 중에는 보유를 유지한다.
2. **Preview는 실행하지 않는다.**
3. **RB 100%는 Core 100%다.** 방어 모드로 해석하지 않는다.
4. **주문은 사람이 한다.** 이 시스템의 승인 범위는 목표 비중 산출과 안전장치까지다. 주문 자동화는 승인되지 않았고, 하려면 별도 설계·검증·승인이 필요하다. 첫 3~6개월은 실시간(LIVE) 잠금 기록을 쌓으며 관찰한다.
5. 운영 설정: `ADAPTIVE_MODE`는 `reference_only`(기본) 또는 `core_only`만 운영에 쓴다. `OFFICIAL_REQUIRES_F2R_PUBLISHED`·`OFFICIAL_REQUIRES_AUTHOR_CORE`는 워크플로에서 "1"로 고정돼 있고, 바꾸려면 PR이 필요하다(코드의 "0" 비상 해제는 쓰지 않는다).
6. 권한: 협업자를 두지 않는다, classic PAT를 쓰지 않는다, GitHub App은 필요할 때만 이 저장소에 한정한다, 2단계 인증을 쓴다.
7. **`docs/data`는 사람이 직접 고치지 않는다.** 잠금·감사·해제 기록은 추가 전용이다. 삭제·수정이 꼭 필요하면 `PDS_HALT`를 건 상태에서, 사유를 적은 별도 PR로 소유자의 명시 승인을 받아 한다.
   - 주의: 파이프라인의 추가 전용 검사는 **한 실행 안에서** 기존 기록이 바뀌는 것만 막는다(실행 시작 때 읽은 파일과 비교) [코드]. 사람이 커밋으로 바꾼 파일은 다음 실행이 새 기준으로 그대로 읽는다. 사람의 변경을 막는 것은 PR 검토와 CI(실데이터 테스트의 원작자 Core 대조 개월 수 ≥ 116 등)뿐이다.
   - 마지막 잠긴 달을 지우면 다음 실행이 그 달을 다시 판정한다(마감이 지났으면 BLOCKED). 중간 달을 지우면 빈 달이 되어 다시 채워지지 않는다 [코드 판독].

### 주의사항
- 원작자가 F2R JSON·워크북의 주소·형식·공개 시각을 바꾸면 매달 대기 → 보류가 될 수 있다(안전 쪽 실패). 원작자 의존이 이 시스템의 가장 큰 운영 위험이다.
- 10일 예약 실행이 23:59:59 UTC를 넘겨 시작되면 자료가 완비돼도 보류된다. 늦으면 수동 실행으로 대응한다(② 9.1절).
- 운영자 중지는 실행 시작 때 한 번 읽힌다. 이미 돌고 있던 실행은 막지 못한다(② 7.3절 절차).
- 1인 저장소의 수동 해제 승인은 본인 재확인이다. 계정 탈취·PAT 유출은 막지 못한다.
- Telegram이 설정되지 않으면 알림이 조용히 생략된다. 실패 메일을 함께 켠다.
- 추이 이력(116개월)은 사후 재구성이며 두 규칙이 섞여 있다. 성과 평가에는 앞으로 쌓일 LIVE 기록만 쓴다.
- 잠금 파일의 원본은 git 이력뿐이다. 현재 코드로 다시 설치하면 같은 이력이 나오지 않는다.
- IRP 대체 ETF의 규정상 분류·매수 가능 여부는 확인되지 않았다.
